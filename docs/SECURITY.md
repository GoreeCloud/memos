# GoreeCloud Memos — Security Boundaries

The initial code is a single-user development preview, not a hardened multi-tenant service.

- Server refuses startup without a token of at least 24 characters; choose a cryptographically random secret.
- Binds to 127.0.0.1 by default; use a separately reviewed HTTPS reverse proxy before any network exposure.
- Data routes require a constant-time bearer token check; health and web static assets reveal no note content. A shared, in-memory per-socket-peer guard blocks API access for the rest of a 60-second window after eight failed authentication attempts (HTTP 429, `Retry-After: 60`). Authentication decisions and failure accounting use one lock, so simultaneous threads cannot bypass the same peer's counter through a check/record race. A successful authentication before lock clears that peer's failures. Source is `server/auth_guard.py` with live HTTP and concurrent regression tests.
- No authentication cookies, permissive CORS, third-party scripts or user-supplied HTML rendering.
- Stale versioned writes return HTTP 409 rather than silently overwriting data. The browser editor's previous-version restore asks for explicit confirmation (including an unsaved-draft warning) and submits the displayed memo's version in PATCH; a conflict leaves the editor draft intact. Prior revisions are presented with textContent, not HTML interpretation. A client-side confirmation is an accident-prevention guard, not an independent authorization control.
- Known memo fields, color values, JSON sizes and maximum text lengths are validated.
- SQLite queries use bound parameters and memo bodies are displayed with DOM textContent.
- Browser token lives only in tab memory, note drafts in sessionStorage, and layout/theme in localStorage. The **Lock workspace** button forgets the in-memory token, closes the editor, and clears displayed memo content; pending feed replies are invalidated so they cannot repopulate a locked view. Lock intentionally preserves sessionStorage drafts, which can be reloaded after fresh authentication. This is a client-side privacy control, not server-side token revocation; an already copied token remains valid until the server operator rotates it. Users can explicitly **Clear drafts** before or after authentication; a confirmation is required to remove Memos draft keys (including quick capture) from the current tab, and an open editor is closed afterward. Other session keys, saved server notes, tokens, and layout/theme preferences are left alone. Drafts are not automatically deleted on authentication failure, to avoid unexpectedly losing unsaved work. Five browser-logic regression tests verified this selective clearing in GitHub CI. This does not guarantee secure deletion of browser-managed storage or operating-system copies.
- Data is not encrypted by this app at rest. On POSIX hosts, the recommended **private development launcher** (`server/serve_private.py`) binds only to IPv4 loopback, validates the token before touching storage, and provisions a 0700 directory and 0600 database through the existing fail-closed helper. That helper now uses no-follow directory descriptors, rejects ancestor and database symlinks, and creates missing intermediate directories with 0700 permissions. It does not audit existing ancestors' ownership or ACLs. It sets process umask 077 for newly created files. For existing database files it also verifies SQLite integrity, schema and revision history before any server schema initialization, rejecting damaged or uninitialized files without overwriting them. The legacy `server/app.py` startup **does not** enforce these checks automatically; unsafe existing permissions require separate operator remediation. See [private storage](PRIVATE_STORAGE.md).
- JSON v2 export includes all memos and revision history, including trash, without the 2,000-result feed cap; treat it as sensitive data. The CLI's optional `export --output PATH` creates a private 0600 POSIX file with exclusive publication and failure cleanup, but the JSON remains plaintext. Legacy stdout export and shell redirection do not enforce those file permissions; see [backup and recovery](BACKUP_AND_RECOVERY.md).
- Safe Markdown subset rendering uses DOM elements and text nodes, never unsanitized HTML. External link hrefs only accept HTTP(S) with noreferrer/noopener. Both the renderer and link policy have Node.js regression tests.
- The Python CLI and native GTK4 client now reject HTTP redirects and environment-configured HTTP proxy routing when sending bearer tokens. They require HTTPS for non-loopback API hosts; cleartext HTTP is accepted only for numeric loopback addresses (such as `127.0.0.1` and `[::1]`). GTK transport policy is statically checked by CI, not exercised in a graphical integration test.
- A single shared instance token is not a user account or authorization system. The per-peer authentication guard is a process-local development safeguard, not distributed or production-grade throttling. It ignores untrusted `X-Forwarded-For`, stores at most 1,024 tracked peers, resets on process restart, and can temporarily lock out an authorized user sharing the same peer IP. Concurrent attempts and peer-table eviction limit protection; network exposure still requires separately reviewed TLS, identity and abuse controls.
- Consistency-aware online SQLite backup, read-only verify and non-overwriting restore commands are included. Backups are not encrypted, scheduled, retained or externally replicated. See BACKUP_AND_RECOVERY.md. Additional recovery drills remain required before production.
- GC UI token alignment does not establish platform-wide visual/accessibility approval.
- Threats still to resolve: distributed/proxy-aware production rate limits and abuse protection, identity/SSO, comprehensive audit logging, migration safety, attachment scanning and quotas, authenticated AI/webhook access, secret rotation, TLS, disaster recovery and accessibility QA.
